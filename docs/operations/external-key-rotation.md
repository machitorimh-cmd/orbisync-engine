# 外部認証の署名鍵の更新

外部認証の有効なサーバーでは、管理Consoleの「外部認証の鍵更新」、または `POST /v1/auth/external/keys/reload` で、設定済みの `auth.external.jwks_path` を再読み込みできます。操作には `admin.auth.keys.reload` が必要です。リクエストからパスやURLを指定する機能はありません。

## 鍵を更新する手順

1. 新しい署名鍵には新しい `kid` を付け、旧鍵と新鍵の公開鍵を同じJWKSへ含めます。稼働中のファイルを部分的に書き換えず、完成したファイルを同じ場所へ原子的に差し替えます。
2. 再読み込みを実行し、返された `generation`、`key_count`、`key_ids` と、`auth.external_keys.reload` の成功監査を確認します。generationはプロセス再起動で1へ戻ります。
3. 外部IdPを新鍵による署名へ切り替えます。旧署名tokenの受け入れが必要な間は旧鍵もファイルに残します。
4. 重複期間が終わったら旧鍵を除いたJWKSを配置し、再読み込みします。以降、その `kid` による新しい外部認証は拒否されます。

OrbiSyncが既に発行したセッションには別の有効期限があります。外部の旧鍵を除くだけでは失効しません。セッション自体も止める場合は、[セッション管理](authentication-sessions.md)の個別・全件失効を使用します。

## 検証と障害時の動作

ファイルは256 KiB以下、鍵は1～64件、`kid` は一意の1～128バイトで制御文字を含まないことが必要です。設定されたalgorithmだけを受け入れます。Ed25519の公開点、P-256の公開点、2048～8192ビットRSA公開鍵と指数も検証します。署名を検証できない長さの値をbase64として読み込めただけでは採用しません。issuer・audience・algorithmの設定は変わりません。

候補全体の検証と必須監査の保存が成功してから、鍵集合を一度に切り替えます。不正な候補は400、監査などの障害は503となり、稼働中の鍵を維持します。不正ファイルの拒否も失敗監査に残します。応答には鍵本体・秘密鍵・ファイルパスを含めません。

操作がタイムアウトした場合は、監査と稼働世代を確認してから再試行します。認可済みの更新は、HTTPクライアントが切断しても監査・切り替えを完了させます。複数プロセスを運用する場合、ローカルファイルと再読み込みは各プロセスで行います。
