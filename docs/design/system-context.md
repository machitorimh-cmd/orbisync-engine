# OrbiSync システムコンテキスト設計

## 1. 文書の位置づけ

本書は `metaverse_core_specification.md` を、実装開始時にシステム境界と責務を判断できる粒度へ具体化する。原仕様の置き換えではない。原仕様と本書が競合する場合は原仕様を優先し、未決定事項は ADR で確定する。

記述上の区分は次のとおりとする。各節の見出し、表の状態列、または段落冒頭のラベルで判別する。ラベルのない引用・要約は作らない。

- **[SPEC] 仕様由来の確定事項**: 仕様書で要求または禁止されている事項
- **[REC] 設計上の推奨**: 要求を満たすための設計案。実装前にレビューする
- **[ADR] ADR 待ち**: 複数案が成立し、現時点では確定しない事項

## 2. システムの目的

**[SPEC]** OrbiSync は、複数の認証済みクライアントが同一ワールドに参加し、ユーザー、汎用エンティティ、位置、向き、状態、イベントをリアルタイム共有するための、用途・描画・アセット非依存のヘッドレスな OSS バックエンドである（仕様 §1, §47）。

完成済みアプリケーションやレンダラーを提供するのではなく、公開 REST API、公開リアルタイムプロトコル、SDK 生成材料を提供する。公式参照クライアントだけが利用できる非公開操作は設けない（仕様 §3.2）。

## 3. システム境界

```text
                              ┌─────────────────────────┐
                              │ 組織管理者・運用者       │
                              └───────────┬─────────────┘
                                          │ 公開管理 API
┌─────────────────────────┐               │ HTTPS/JSON
│ エンドユーザー           │               │
│ 任意クライアント/SDK     ├──────┐        │
└─────────────────────────┘      │        │
                                 │ HTTPS + WSS
┌─────────────────────────┐      │ 公開 API / protocol
│ 最小参照実装             ├──────┤
│ 疎通・E2E・SDK利用例     │      │
└─────────────────────────┘      ▼
                       ┌───────────────────────────────┐
                       │ OrbiSync の境界               │
                       │                               │
                       │ ID/権限、World/Instance       │
                       │ Identity Session / Realtime   │
                       │ Presence、状態同期            │
                       │ 検証、Interest、永続化調停    │
                       │ 監査、観測、外部拡張窓口      │
                       └───────┬───────────┬───────────┘
                               │           │
                         SQL   │           │ Webhook/HTTP
                               ▼           ▼
                       ┌────────────┐  ┌──────────────────┐
                       │ PostgreSQL │  │ 外部拡張サービス │
                       └────────────┘  └──────────────────┘
```

### 3.1 境界内の責務 [SPEC]

| 責務群 | OrbiSync が保証する責務 |
|---|---|
| Identity / Access | ローカル ID・パスワード認証、Identity Session とトークン、ユーザー、ロール、権限（仕様 §4.1, §19） |
| World lifecycle | ワールド定義および実行中ワールドインスタンスの管理（仕様 §9.3, §9.4） |
| Realtime Connection / Presence | socket 接続、入室、退室、再接続時の binding、プレゼンス、状態復元。Identity Session は所有しない（仕様 §9.5） |
| State Authority | ユーザーと汎用エンティティの状態、所有権、操作権限、サーバー権威型の入力検証（仕様 §11） |
| Realtime Delivery | スナップショット、差分、イベントの配信。Protobuf を本番形式とする（仕様 §13.3, §14） |
| Distribution | Interest Management と不安定な回線からの復帰（仕様 §16, §17） |
| Data | 一時状態と永続状態の分離、チェックポイント（仕様 §10） |
| Integration | 公開 API、公開プロトコル、外部拡張 API、SDK 生成材料（仕様 §23, §24） |
| Operations | 管理 API、監査ログ、メトリクス、ログ、トレース（仕様 §27） |
| Project tooling | Core 実行サーバーの外から公開 API / protocol を駆動する負荷試験ツールの提供（仕様 §4.1） |

Identity Session と Realtime Connection / Presence は別のライフサイクルと識別子を持つ。**[REC]** 前者を `AuthSessionId`、後者を `RealtimeConnectionId` と `PresenceId` で識別する。Realtime 側は資格情報を所有・失効せず、Identity 側の検証結果を Application coordinator 経由で受けて binding する。

### 3.2 境界外の責務 [SPEC]

レンダリング、アセット、音声・映像、UI、端末固有 UI、用途固有業務、決済・NFT、SNS、ワールドエディタ、物理エンジン、高度なゲームロジック、AI キャラクター、コンテンツモデレーション業務は OrbiSync の責務ではない（仕様 §4.2）。

境界外機能との連携が必要でも、コアのドメインモデルへ用途固有概念を追加せず、公開 API、公開プロトコル、外部拡張境界で接続する。

### 3.3 外部主体と契約 [SPEC]

| 主体 | OrbiSync に対する責務 | OrbiSync から受ける契約 |
|---|---|---|
| 組織管理者 | ユーザー発行、権限付与、ワールド管理 | 認証済みの管理 REST API、監査可能な結果 |
| エンドユーザー | 組織発行資格情報で認証し、許可された入力のみ送信 | 接続、入退室、状態同期、再接続 |
| クライアント/SDK 開発者 | OpenAPI、`.proto`、状態遷移、テストベクトルへ準拠 | 言語・描画方式に依存しない公開契約 |
| 運用者 | PostgreSQL、TLS 終端、設定、バックアップ、監視基盤を運用 | OCI イメージ、ヘルス情報、メトリクス、ログ、トレース |
| 外部拡張サービス | 公開された認証・再試行・冪等性契約へ準拠 | Webhook / HTTP の拡張境界 |
| PostgreSQL | 永続データの保全 | OrbiSync からの SQL 接続 |
| 負荷試験ツール | 実行サーバー外から認証・接続・状態同期を再現 | Core project が提供する実行可能な試験ツールと結果出力 |

TLS 終端を OrbiSync プロセスが担うかリバースプロキシが担うかは仕様上未確定である。外部公開面では HTTPS/WSS を必須とし、配置方式は ADR 候補とする。

## 4. ドメインモデル概要

**[SPEC]** 仕様 §9 に定義される主要ドメイン概念：

| 概念 | 識別子 | 主な属性 |
|---|---|---|
| User | `UserId` | login_id, display_name, status, must_change_password |
| Role / Permission | `RoleId` | 名前空間付き権限文字列の集合 |
| WorldDefinition | `WorldId` | name, status, default_spawn, capacity, metadata, revision |
| WorldInstance | `InstanceId` | world_id, lifecycle, capacity, revision |
| Entity | `EntityId` | instance_id, kind, owner, transform, state, visibility, revision |
| Transform | — | position(Vec3), rotation(Quaternion), scale(Vec3) |

**[REC]** 設計文書上の所有モジュール対応は `architecture.md` §3 に定める。

**[SPEC]** 座標系は右手系 Y-up、Quaternion は `x, y, z, w` の順、1 unit = 1 meter をデフォルトとする（仕様 §9.7）。NaN、Infinity、範囲外値を拒否する。

**[SPEC]** エンティティ状態はコア標準コンポーネント（`core.transform` 等）と名前空間付きカスタムコンポーネント（`com.example.door` 等）の 2 方式を併用できる（仕様 §9.8）。カスタム状態はサイズ上限、更新頻度上限、権限を持つ。

## 5. 主要ユースケース

以下のシナリオ分解と完了条件は **[REC]** である。機能範囲は [SPEC] に基づくが、手順、ID、失敗時の扱いは後続仕様および ADR と照合して確定する。

### UC-01 組織管理者が利用者を利用可能にする

1. 管理者を認証・認可する。
2. ローカル ID を重複検証し、パスワードを Argon2id で安全にハッシュ化する。
3. ユーザーと必要なロール/権限を永続化する。
4. 監査記録を残し、公開管理 API から結果を返す。

**完了条件:** 作成された利用者が公開 API で認証でき、管理者専用権限を暗黙に取得しない。

### UC-02 利用者がワールドへ入室する

1. HTTPS で資格情報を認証し、Identity が `AuthSessionId` に紐づくトークンを発行する。
2. WSS 接続時に Application coordinator が Identity へ Identity Session の検証を依頼する。
3. 対象ワールド/インスタンスへのアクセス権を検証する。
4. Realtime が別の `RealtimeConnectionId` を発行し、参加成立時に `PresenceId` を認証済み主体へ binding する。
5. インスタンスへ参加させ、Interest Management 適用後の初期スナップショットとプレゼンス更新を配信する。

**完了条件:** 本人には現在状態が返り、許可された既存参加者には入室が観測される。

### UC-03 利用者が状態を更新する

1. クライアント入力を公開プロトコル型として受信する。
2. 認証、所属インスタンス、所有権/操作権限、入力値（有限性、速度、頻度、境界）を検証する。
3. インスタンス内の正準状態を更新する。
4. Interest Management により受信者を選択する。
5. プロトコル型へ変換し、差分またはイベントを配信する。
6. 永続対象または監査対象のみを非同期または同期で記録する。

**完了条件:** 未認可入力は状態を変えず、許可されたクライアントにはサーバーが確定した状態が届く。

### UC-04 モバイル回線切断後に復帰する

1. 切断を検知し、即時に同一人物の二重参加として確定しない猶予を持つ。
2. Identity Session の有効性は Identity が検証し、Realtime は別管理の resume binding を検証する。
3. 復帰可能なら既存参加状態へ再関連付けし、不可能なら新規同期へフォールバックする。
4. 欠落差分または最新スナップショットを送り、現在状態へ収束させる。

**完了条件:** クライアントが古いローカル状態を正準状態として上書きせず、現在のサーバー状態へ復帰する。

再接続猶予、復帰情報、差分保持範囲の具体値は仕様 §16 で推奨初期値が示されているが、確定値は後続仕様または ADR で扱う。

### UC-05 外部サービスが用途固有機能を付加する

1. OrbiSync が公開拡張境界へ、安定した識別子と汎用イベントを渡す。
2. 外部サービスが用途固有処理を行う。
3. 状態変更が必要なら、外部サービスも公開 API/プロトコルと権限検証を経由する。

**完了条件:** 外部サービス障害がインスタンス実行ループを無制限に停止させず、公式 UI 専用の裏口を必要としない。

拡張方式、配送保証、同期/非同期、失敗時ポリシーは要 ADR とする。

### UC-06 運用者が障害を検知・追跡する

1. メトリクスでサービス/接続/インスタンスの健全性を検知する。
2. 相関可能な構造化ログとトレースで処理経路を追跡する。
3. 監査ログで管理操作とセキュリティ上重要な操作を追跡する。

**完了条件:** 機密情報をログへ露出せず、失敗した要求を API 入口から永続化/配信まで関連付けられる。

### UC-07 エンティティを生成・更新・削除する

1. 権限を持つクライアントがエンティティ操作を要求する。
2. サーバーが所有権、操作権限、カスタムコンポーネントのサイズ/頻度を検証する。
3. 正準状態を更新し、Interest 範囲内のクライアントへ配信する。
4. 所有権移譲は監査可能にする。

**完了条件:** クライアントの自己申告 owner を信用せず、サーバーが所有権を確定する（仕様 §20.3）。

## 6. 運用・配置コンテキスト

**[SPEC]** 初期の利用形態として、匿名ユーザーなし、自己登録なし、外部ログインなし（仕様 §3.3）。

**[REC]** 仕様 §3.3 は「1インスタンス = 1組織」を標準運用形態として示す。これは組織モデルの初期方針であり、process/database/deployment topology の規定ではない。

**設計前提** ADR-009によりv1は1 deployment = 1 organization、1 server process、1 PostgreSQL logical database/schema、reverse proxy TLS終端とする。

**[SPEC]** Docker Compose でセルフホスト可能であること（仕様 §3.3）。

**[SPEC]** 小規模環境では 1 台の Linux server で運用可能とする（仕様 §5.1）。これは運用能力の要件であり、組織と process/database/schema の対応を確定しない。

```text
Internet
   │ HTTPS/WSS
   ▼
[TLS endpoint] ── [OrbiSync single binary] ── [PostgreSQL]
                           │
                           ├── metrics/logs/traces ── [運用基盤]
                           └── extension calls ───── [外部サービス]
```

**[SPEC]** 水平分割は初期完了条件ではない（仕様 §5.2）。**[REC]** 組織、ワールド、ワールドインスタンス、接続の識別子をプロセスローカルな値だけにせず、将来ルーティング可能な境界を保つ。

## 7. 制約と品質上の含意

- **[SPEC]** 匿名利用、自己登録、外部 IdP、マルチテナントは初期対象外である（仕様 §3.3）。
- **[SPEC]** 4G/5G を含む不安定な回線での切断・遅延と復帰を扱う（仕様 §16）。
- **[REC]** 重複・順序変化への耐性は protocol sequence / idempotency の ADR 候補として検証する。
- **[SPEC]** 単一バイナリ性とモジュール分離を両立し、プロセス分割を初期の前提にしない（仕様 §7.1）。
- **[SPEC]** ドメイン処理はレンダラー、ゲームエンジン、アセット形式を認識しない（仕様 §3.2）。
- **[SPEC]** 1000 人同時参加や高度な物理・チート対策は保証しない（仕様 §5.2）。実測前に容量保証値を置かない。
- **[SPEC]** 任意の第三者コードをコアプロセスへロードしない（仕様 §23.1）。拡張はプロセス外境界を基本とする。
- **[SPEC]** 公開契約の正本は `.proto`、OpenAPI、状態遷移仕様、互換性テストベクトルであり、SDK 実装を正本にしない（仕様 §8.2）。
- **[SPEC]** 位置履歴をデフォルトで永続保存しない。ログへパスワード、token、完全な payload を出さない（仕様 §26.4）。

## 8. 矛盾・曖昧さ・要確認事項

| ID | 事項 | 推奨案と根拠 | 状態 |
|---|---|---|---|
| CTX-01 | 仕様表題/本文の `metaverse-core` と名称 `OrbiSync` が混在する | ADR-001で公開名`OrbiSync`、server binary`orbisync-server`、Rust package接頭辞`orbisync-*`に統一。原仕様内の旧名は仮称・例として保持 | Accepted |
| CTX-02 | 「1インスタンス」が組織単位の利用形態とワールドインスタンスの両方を指し得る | 組織側の配置単位を **deployment**、実行ワールドを **world instance** と設計文書・コードで呼び分ける | [REC]/[ADR] |
| CTX-03 | 外部拡張 API に Webhook / HTTP / gRPC が併記され、必須方式が不明 | 初期は outbound Webhook と認証済み REST の必要最小限を候補とし、gRPC は実測後に選ぶ | [ADR] |
| CTX-04 | TLS 終端の所有者が不明 | 外部通信の HTTPS/WSS は必須、プロセス内 TLS とリバースプロキシ終端の双方を許容する配置契約を ADR で定義する | [ADR] |
| CTX-05 | 監査ログの永続先と改ざん耐性が不明 | 初期は PostgreSQL を候補とし、保持期間・閲覧権限・外部エクスポート要件を先に確定する | [ADR] |
| CTX-06 | 最小参照実装の提供範囲は MAY | コア API の E2E/互換性確認に必要な最小クライアントだけを別成果物として計画し、コア実装の完了条件とは分ける | [REC] |
| CTX-07 | deployment/process/database topology が不明 | 最小 Compose 構成の検証を先行し、組織ごとの分離単位はセキュリティ・運用要件を確認して ADR 化する | [ADR] |
| CTX-08 | Access Token形式 | ADR-002で15分のEd25519署名JWT、Active AuthSession確認、30日rotating Refresh Token、Realtime接続ticketに確定 | Accepted |

## 9. 仕様から意図的に確定しない事項

ドメイン属性の詳細、権限一覧の最終形、状態分類の具体的境界、プロトコルメッセージの最終定義、再接続アルゴリズムの具体値、Interest Management のチューニング値、性能 SLO、監査イベント一覧は後続設計または ADR の検討対象である。本書では境界だけを示し、先取りして確定しない。
